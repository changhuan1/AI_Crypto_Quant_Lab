# 量化交易平台后续研究方案、建设流程与技术架构

## 1. 总体目标

后续研究和开发的总目标，是把当前项目从“本地量化脚本集合”升级为“类似聚宽的量化研究与交易平台”。

最终平台应该做到：

- 数据由平台后台自动维护。
- 用户通过网页创建、配置、回测和运行策略。
- 用户不需要直接运行命令行脚本。
- 策略运行过程可解释、可追踪、可复盘。
- 平台支持 A 股为主，Crypto 为辅。
- 先做本地单用户版本，再逐步升级为多人平台。

## 2. 研究主线

后续研究分为 6 条主线。

### 2.1 数据工程研究

目标：

- 建立稳定的数据采集、清洗、存储和质量检查系统。

研究内容：

- A 股行情数据源对比：AKShare、Tushare、BaoStock、聚宽数据接口。
- 复权价格处理。
- 停牌、涨跌停、ST、退市风险处理。
- 指数成分股历史变化。
- 交易日历维护。
- 数据缺失检测和自动补齐。

核心问题：

- 数据是否可靠。
- 数据是否可复现。
- 回测是否使用了未来数据。
- 每天数据是否能自动更新。

### 2.2 策略 API 研究

目标：

- 设计类似聚宽的简单策略接口。

研究内容：

- `initialize(context)`。
- `before_trading_start(context, data)`。
- `handle_data(context, data)`。
- `after_trading_end(context, data)`。
- `get_price()`。
- `get_index_stocks()`。
- `order_target_percent()`。
- `history()`。

核心问题：

- 用户写策略时是否足够简单。
- 平台是否能控制风险和权限。
- 策略代码是否能安全运行。

### 2.3 回测引擎研究

目标：

- 做出可信的 A 股日频回测引擎。

研究内容：

- 撮合模型。
- 手续费和印花税。
- 滑点模型。
- 涨跌停处理。
- 停牌处理。
- 调仓频率。
- 仓位管理。
- 订单、成交、持仓、现金流水。

核心问题：

- 回测结果是否真实。
- 是否过度乐观。
- 是否能解释每一笔交易。

### 2.4 策略模板研究

目标：

- 为平台提供可直接使用的策略模板。

第一批模板：

- 上证成分股动量轮动。
- 上证成分股均线择时。
- 宽基指数择时。
- 多因子选股。
- 低波动选股。
- Crypto BTC/ETH 轮动。

核心问题：

- 模板是否容易理解。
- 参数是否能可视化配置。
- 策略是否能复用同一个回测引擎。

### 2.5 风控体系研究

目标：

- 把风控做成平台底层能力，而不是每个策略自己写一遍。

研究内容：

- 市场风险状态。
- 单票仓位限制。
- 总仓位限制。
- 最大回撤预警。
- 流动性过滤。
- ST 和退市风险过滤。
- 连续亏损暂停策略。
- 策略异常下线。

核心问题：

- 平台能否阻止明显危险的策略。
- 风控是否能被用户看懂。
- 风控是否能记录触发原因。

### 2.6 平台产品研究

目标：

- 做出非程序员也能使用的量化平台。

研究内容：

- 策略中心怎么设计。
- 回测结果怎么展示。
- 买卖原因怎么解释。
- 数据中心怎么让用户放心。
- 任务中心怎么显示自动化运行状态。
- 模拟交易如何降低用户理解成本。

核心问题：

- 用户是否不用看代码也能理解系统。
- 用户是否能独立完成策略创建和回测。
- 用户是否知道系统今天做了什么。

## 3. 建设流程

建议按“先平台骨架，再策略能力，再自动化运行，再多人化”的顺序推进。

### 阶段 0：方向重置

目标：

- 明确系统不再只是个人量化脚本，而是量化平台。

产出：

- 平台需求分析文档。
- 后续研究路线文档。
- 新的目录架构规划。

验收标准：

- 文档能回答系统做给谁用。
- 文档能回答用户怎么使用。
- 文档能回答后台负责什么。

### 阶段 1：平台核心抽象

目标：

- 建立平台底层对象和统一接口。

任务：

1. 新建 `src/platform`。
2. 定义 `Strategy`。
3. 定义 `StrategyConfig`。
4. 定义 `Context`。
5. 定义 `DataPortal`。
6. 定义 `Order`、`Trade`、`Position`、`Account`。
7. 定义策略生命周期函数。

产出：

- 平台核心对象。
- 简单策略运行器。
- 第一个策略模板能通过平台接口运行。

验收标准：

- 策略不直接读数据库。
- 策略不直接调用 AKShare。
- 策略通过统一 API 获取数据。

### 阶段 2：数据中心

目标：

- 后台统一维护数据，让用户不用手动处理数据。

任务：

1. 整理 `assets` 表。
2. 整理 `prices_daily` 表。
3. 增加 `index_constituents` 表。
4. 增加 `trading_calendar` 表。
5. 增加数据质量检查。
6. 增加数据更新页面。

产出：

- 数据中心页面。
- 数据更新按钮。
- 数据质量报告。

验收标准：

- 用户能在页面看到最新数据日期。
- 用户能看到股票池数量。
- 用户能看到数据是否缺失。
- 用户能点击按钮更新数据。

### 阶段 3：策略中心

目标：

- 用户可以在网页上创建和管理策略。

任务：

1. 建立策略列表。
2. 建立策略详情页。
3. 建立策略模板库。
4. 建立参数配置表单。
5. 保存策略配置。
6. 保存策略版本。

产出：

- 策略中心页面。
- 策略模板页面。
- 策略参数配置页面。

验收标准：

- 用户能创建一个“上证成分股动量轮动策略”。
- 用户能修改最大持仓数、调仓频率、仓位上限。
- 用户能保存策略。

### 阶段 4：一键回测

目标：

- 用户不用命令行，在网页点击按钮完成回测。

任务：

1. 改造回测引擎。
2. 建立回测任务对象。
3. 建立回测参数页面。
4. 建立回测结果表。
5. 保存净值、持仓、订单、交易和指标。
6. 展示回测结果。

产出：

- 回测中心页面。
- 回测结果页面。
- 交易流水页面。

验收标准：

- 用户选择策略和日期后能点击运行回测。
- 回测结果能保存。
- 页面能展示收益、回撤、净值、持仓、交易。
- 每笔交易有原因。

### 阶段 5：模拟交易

目标：

- 从历史回测进入每日模拟运行。

任务：

1. 建立模拟账户。
2. 每日生成目标持仓。
3. 生成调仓建议。
4. 保存模拟订单。
5. 保存模拟成交。
6. 更新模拟净值。

产出：

- 模拟交易页面。
- 今日信号页面。
- 模拟账户页面。

验收标准：

- 每天能生成买入、卖出、持有列表。
- 不重复下单。
- 不超过仓位限制。
- 每个信号都有解释。

### 阶段 6：任务调度与自动化

目标：

- 平台自动运行，不依赖用户每天手动点。

任务：

1. 增加任务调度器。
2. 自动更新行情。
3. 自动计算因子。
4. 自动运行策略。
5. 自动生成模拟订单。
6. 自动生成日报。

产出：

- 任务中心页面。
- 任务日志。
- 每日策略报告。

验收标准：

- 用户打开平台即可看到今日结果。
- 任务失败时能看到错误原因。
- 任务可以手动重跑。

### 阶段 7：风控中心

目标：

- 将风控规则平台化、可视化。

任务：

1. 建立风控规则引擎。
2. 建立市场风险状态。
3. 建立组合风险检查。
4. 建立资产级风险检查。
5. 记录风险事件。
6. 可视化风险解释。

产出：

- 风控中心页面。
- 风险事件表。
- 风控解释模块。

验收标准：

- 用户能看到当前风险状态。
- 用户能看到为什么不能买某只股票。
- 用户能看到策略是否触发风控。

### 阶段 8：平台化升级

目标：

- 从本地单用户工具升级为可多人使用的平台。

任务：

1. 引入用户系统。
2. 引入 PostgreSQL。
3. 引入 FastAPI 后端。
4. 引入独立前端。
5. 引入权限管理。
6. 引入任务队列。

产出：

- Web 后端服务。
- 独立前端应用。
- 多用户策略管理。

验收标准：

- 不同用户能管理自己的策略。
- 策略、回测、模拟账户互相隔离。
- 平台可长期运行。

## 4. 技术架构

## 4.1 MVP 技术架构

第一版继续用轻量架构，快速跑通平台体验。

```text
Streamlit Web
    |
    | 调用
    v
Platform Service Layer
    |
    | 使用
    v
Data API / Strategy Runner / Backtest Engine / Risk Engine
    |
    | 读写
    v
DuckDB
    |
    | 数据来源
    v
AKShare / CCXT / Local Files
```

技术选型：

- Python。
- Streamlit。
- DuckDB。
- Pandas。
- Plotly。
- AKShare。
- CCXT。
- APScheduler。

适合阶段：

- 本地单用户。
- 快速研究。
- 快速验证平台交互。

## 4.2 标准平台架构

当 MVP 跑通后，建议升级为标准 Web 平台。

```text
React / Next.js Frontend
    |
    | HTTP API
    v
FastAPI Backend
    |
    | 业务服务
    v
Strategy Service / Backtest Service / Data Service / Risk Service
    |
    | 异步任务
    v
Celery or Prefect Worker
    |
    | 存储
    v
PostgreSQL + DuckDB + Redis
    |
    | 数据源
    v
AKShare / Tushare / Exchange APIs / Broker APIs
```

技术选型：

- 前端：React 或 Next.js。
- 后端：FastAPI。
- 主数据库：PostgreSQL。
- 分析数据库：DuckDB，后续可升级 ClickHouse。
- 缓存和任务状态：Redis。
- 任务队列：Celery、RQ 或 Prefect。
- 图表：ECharts、Plotly 或 TradingView Lightweight Charts。
- 策略运行沙箱：独立 Python 进程，后续可 Docker 隔离。

适合阶段：

- 多用户。
- 长期运行。
- 策略托管。
- 更接近商业化平台。

## 4.3 数据架构

建议分三类数据。

### 4.3.1 原始数据

来源数据，尽量保留原貌。

表：

- raw_prices_a_share
- raw_prices_crypto
- raw_index_constituents
- raw_calendar

用途：

- 追溯数据源。
- 重算清洗数据。
- 发现数据问题。

### 4.3.2 标准化数据

平台策略统一使用的数据。

表：

- assets
- prices_daily
- index_constituents
- trading_calendar
- features_daily

用途：

- 策略读取。
- 因子计算。
- 回测使用。

### 4.3.3 业务数据

平台运行产生的数据。

表：

- strategies
- strategy_versions
- backtest_runs
- portfolio_nav
- positions_daily
- orders
- trades
- risk_events
- job_runs

用途：

- 管理策略。
- 展示回测。
- 模拟交易。
- 审计和复盘。

## 4.4 策略架构

策略应该被设计成平台对象。

```text
Strategy
    |
    +-- metadata
    +-- code or template_id
    +-- config
    +-- version
    +-- status
    +-- runs
```

策略运行流程：

```text
加载策略
  |
加载配置
  |
创建 Context
  |
注入 Data API
  |
运行 initialize
  |
按交易日循环
  |
运行 before_trading_start
  |
运行 handle_data
  |
生成订单
  |
风控检查
  |
撮合成交
  |
更新账户
  |
保存结果
```

## 4.5 回测架构

回测引擎分为 6 个组件：

- Calendar：交易日历。
- DataPortal：数据访问。
- StrategyRunner：执行策略代码。
- BrokerSimulator：撮合订单。
- Account：账户、现金、持仓。
- MetricsCalculator：指标计算。

关系：

```text
BacktestEngine
    |
    +-- Calendar
    +-- DataPortal
    +-- StrategyRunner
    +-- RiskEngine
    +-- BrokerSimulator
    +-- Account
    +-- MetricsCalculator
```

## 4.6 风控架构

风控分三层。

### 4.6.1 策略前风控

在下单前检查：

- 股票是否停牌。
- 是否 ST。
- 是否涨跌停。
- 是否流动性不足。
- 是否超过单票仓位。
- 是否超过总仓位。

### 4.6.2 组合运行中风控

每日检查：

- 最大回撤。
- 当前波动。
- 持仓集中度。
- 连续亏损。
- 市场风险状态。

### 4.6.3 策略运营风控

策略上线后检查：

- 策略是否连续失败。
- 今日是否生成异常订单。
- 数据是否过期。
- 回测和模拟表现是否严重偏离。

## 5. 版本路线图

- 数据采集。

## 6. 近期最优先任务

接下来不要继续堆单个策略脚本，应该优先做平台骨架。

建议立即做这 5 件事：

1. 新建 `src/platform`。
2. 建立统一数据 API。
3. 建立策略对象和策略配置。
4. 把“上证成分股动量轮动”改造成第一个策略模板。
5. 在 Streamlit 上做“策略中心 + 一键回测”。

最小可用体验应该是：

```text
打开网页
  |
进入策略中心
  |
选择上证成分股动量轮动模板
  |
配置参数
  |
点击运行回测
  |
查看净值、回撤、持仓、交易原因
```

只要这个流程跑通，系统就从“脚本项目”开始真正变成“量化平台”。
