# 成熟量化交易平台需求分析

## 1. 产品定位

本系统不再定位为单个个人量化脚本项目，而是定位为一个类似聚宽的量化研究与交易平台。

平台的核心目标是：

- 普通用户不需要关心数据下载、清洗、存储、复权、交易日历、回测撮合等底层细节。
- 用户主要负责提供策略逻辑，平台负责提供数据、研究环境、回测、模拟交易、实盘接口、风控和可视化。
- 策略开发尽量简单，用户可以通过 Python 策略模板、可视化参数配置、因子选择器、条件组合器等方式创建策略。
- 系统既支持个人研究，也能逐步演进为多人使用的策略平台。

一句话描述：

> 这是一个面向 A 股和数字货币的策略托管型量化平台，用户提交策略，平台负责数据、回测、运行、监控和风控。

## 2. 对标平台

主要参考对象：

- 聚宽 JoinQuant
- 米筐 RiceQuant
- 掘金量化 MyQuant
- BigQuant
- TradingView 策略与信号体系
- Freqtrade 的策略运行和 dry-run 模式

其中聚宽是最重要的参考对象：

- 提供统一数据 API。
- 提供策略研究环境。
- 提供回测系统。
- 提供模拟交易。
- 用户只需要写策略，不需要自己处理底层数据工程。
- 策略运行过程、收益、持仓、订单、日志都可视化。

## 3. 用户画像

### 3.1 初学者用户

特点：

- 不熟悉代码或只懂少量 Python。
- 想用简单条件创建策略。
- 更关心策略是否有效，而不是系统如何实现。

需求：

- 可视化创建策略。
- 使用平台内置模板。
- 一键回测。
- 看得懂收益、回撤、持仓、交易记录。
- 系统解释策略为什么买、为什么卖。

### 3.2 策略研究用户

特点：

- 会写 Python。
- 需要快速验证策略想法。
- 关注因子、择时、轮动、组合优化。

需求：

- 统一数据 API。
- Notebook 或在线研究环境。
- 策略代码编辑器。
- 参数扫描。
- 批量回测。
- 因子分析。
- 基准对比。

### 3.3 策略运营用户

特点：

- 关注策略上线后的稳定性。
- 需要每天看信号、订单、风险和运行日志。

需求：

- 策略监控面板。
- 今日信号。
- 模拟交易账户。
- 风险警报。
- 运行失败通知。
- 策略版本管理。

### 3.4 平台管理员

特点：

- 负责数据源、任务调度、用户权限、系统健康。

需求：

- 数据更新监控。
- 任务调度面板。
- 用户与策略管理。
- 数据质量检查。
- 异常日志追踪。

## 4. 核心业务目标

### 4.1 第一阶段目标

先做一个本地单用户量化平台原型。

目标：

- 用户打开一个 Web 面板。
- 能看到数据是否更新。
- 能选择或编写策略。
- 能点击运行回测。
- 能看到策略结果。
- 能查看买卖信号、持仓、净值、回撤和日志。

### 4.2 第二阶段目标

升级为策略托管平台。

目标：

- 策略保存到平台。
- 策略可以定时运行。
- 平台每天自动更新数据。
- 平台每天自动生成信号。
- 用户只看面板，不手动跑命令。

### 4.3 第三阶段目标

支持多人和实盘前风控。

目标：

- 多用户登录。
- 每个用户有自己的策略、回测和模拟账户。
- 支持策略审批和版本管理。
- 支持模拟交易长期运行。
- 支持接入券商或交易所接口前的风控校验。

## 5. 系统边界

### 5.1 平台负责的事情

- 数据采集。
- 数据清洗。
- 数据存储。
- 股票池维护。
- 交易日历。
- 复权处理。
- 因子计算。
- 回测撮合。
- 交易成本。
- 滑点模型。
- 风险控制。
- 策略调度。
- 结果可视化。
- 日志记录。
- 策略版本管理。

### 5.2 用户负责的事情

- 选择策略模板。
- 配置策略参数。
- 编写少量策略代码。
- 查看回测结果。
- 决定是否进入模拟交易。
- 根据平台信号做人工确认或后续接入实盘。

### 5.3 暂不做的事情

第一版暂不做：

- 真实资金自动下单。
- 高频交易。
- 分布式计算集群。
- 多租户商业化计费。
- 复杂权限体系。
- 社区策略市场。

这些内容可以放到后续版本。

## 6. 核心功能模块

## 6.1 数据中心

数据中心是平台后端能力，普通用户不需要手动运行数据脚本。

### 6.1.1 A 股数据

支持范围：

- 上证指数成分股。
- 后续扩展沪深 300、中证 500、中证 1000、全 A。
- 指数行情。
- 个股日线行情。
- 复权行情。
- 成交额、成交量、换手率。
- 停牌状态。
- ST、退市、上市日期等基础信息。

核心表：

- assets
- prices_daily
- features_daily
- trading_calendar
- index_constituents
- corporate_actions

### 6.1.2 Crypto 数据

支持范围：

- BTC、ETH 等主流币。
- 后续扩展更多交易对。
- 日线、小时线。
- 成交量、成交额。
- 交易所来源。

### 6.1.3 数据质量

需要检查：

- 今日是否更新。
- 是否缺日期。
- 是否缺资产。
- 是否有重复记录。
- 是否出现异常价格。
- 是否出现成交量为 0 的异常数据。

前端需要展示：

- 数据源状态。
- 最新数据日期。
- 股票数量。
- 缺失数据数量。
- 最近一次更新日志。

## 6.2 策略开发中心

这是平台最核心的用户入口。

### 6.2.1 策略模板

内置模板：

- 均线择时策略。
- 动量轮动策略。
- 低波动策略。
- 多因子选股策略。
- 指数增强策略。
- Crypto 轮动策略。

用户可以从模板复制策略，然后修改参数。

### 6.2.2 策略代码接口

参考聚宽风格，提供简单策略函数：

```python
def initialize(context):
    context.max_positions = 30
    context.rebalance_frequency = "weekly"


def before_trading_start(context, data):
    context.stock_pool = get_index_stocks("000001.SH")


def handle_data(context, data):
    candidates = rank_by_factor(context.stock_pool, "momentum_60d")
    target = candidates[:context.max_positions]
    rebalance_to_equal_weight(target)
```

平台需要隐藏底层实现，让用户调用简单 API。

### 6.2.3 可视化策略生成器

面向不懂代码的用户。

示例：

- 股票池：上证指数成分股。
- 买入条件：收盘价高于 120 日均线。
- 排名因子：60 日动量。
- 风险过滤：指数低于 120 日均线时空仓。
- 调仓频率：每周。
- 最大持仓：30 只。

用户通过表单选择后，平台自动生成策略配置。

## 6.3 数据 API 层

平台需要提供稳定、简单、统一的数据 API。

示例 API：

```python
get_price("600519.SH", start_date, end_date)
get_index_stocks("000001.SH", date)
get_factor("600519.SH", "momentum_60d", date)
get_fundamentals("600519.SH", date)
get_current_data("600519.SH")
history("600519.SH", count=120, unit="1d")
```

API 设计原则：

- 用户不直接读 DuckDB。
- 用户不关心 AKShare、CCXT、CSV 或数据库细节。
- 用户只通过平台 API 访问数据。
- API 返回结构要稳定。

## 6.4 回测引擎

回测引擎是平台可信度的核心。

### 6.4.1 必须支持

- 起止日期。
- 初始资金。
- 股票池。
- 调仓频率。
- 买入卖出撮合。
- 手续费。
- 印花税。
- 滑点。
- 停牌处理。
- 涨跌停处理。
- 最大持仓数。
- 单票仓位上限。
- 现金管理。

### 6.4.2 回测输出

需要输出：

- 净值曲线。
- 基准净值。
- 超额收益。
- 年化收益。
- 最大回撤。
- 夏普比率。
- 波动率。
- 胜率。
- 换手率。
- 持仓明细。
- 每日订单。
- 每日交易。
- 每日风险暴露。

### 6.4.3 回测可解释性

每笔交易需要记录原因：

- 因子排名进入前 N。
- 风险状态允许开仓。
- 股票跌破均线被剔除。
- 成交额过滤失败。
- 仓位上限限制。
- 停牌无法交易。

## 6.5 模拟交易中心

模拟交易用于连接回测和实盘。

功能：

- 每日自动生成目标持仓。
- 根据当前持仓生成调仓建议。
- 记录人工确认结果。
- 保存模拟订单。
- 保存模拟成交。
- 跟踪模拟账户净值。
- 检查是否重复下单。
- 检查是否超仓位。

输出：

- 今日应买。
- 今日应卖。
- 今日继续持有。
- 今日禁止买入原因。
- 模拟账户净值。

### 6.6.2 资产风控

- 涨跌停过滤。

## 9. 策略用户体验设计

理想流程：

1. 用户进入策略中心。
2. 点击新建策略。
3. 选择模板，例如“上证成分股动量轮动”。
4. 配置参数。
5. 点击保存。
6. 点击运行回测。
7. 平台展示净值、回撤、持仓、交易记录。
8. 用户点击进入模拟交易。
9. 平台每天自动运行。
10. 用户每天查看今日信号和风险解释。

用户不应该看到：

- 数据下载脚本。
- 数据库 SQL。
- AKShare 细节。
- DuckDB 文件路径。
- 命令行运行流程。

这些都应该进入平台后台。

## 10. 当前项目与目标平台的差距

当前项目已经有：

- A 股行情采集雏形。
- Crypto 行情采集雏形。
- DuckDB 存储。
- 特征计算。
- 简单评分。
- 简单轮动。
- 简单回测。
- Streamlit 面板。

但是当前项目还缺少平台化能力：

- 没有统一策略 API。
- 没有策略管理。
- 没有策略编辑器。
- 没有一键回测入口。
- 没有任务调度中心。
- 没有模拟账户中心。
- 没有完整订单和交易流水。
- 没有清晰的用户流程。
- 没有数据中心页面。
- 没有风控中心页面。
- 没有策略版本管理。

所以当前项目本质还是“量化研究脚本集合”，还不是“量化交易平台”。

## 14. 关键设计原则

### 14.1 用户只面对策略，不面对脚本

错误体验：

### 14.2 后端统一处理数据

用户不应该知道：

- AKShare。
- CCXT。
- DuckDB。
- SQL。
- 数据缺失修复。

用户只应该知道：

- 我选择了什么股票池。
- 我的策略用了什么条件。
- 我的策略赚了还是亏了。
- 为什么买。
- 为什么卖。

### 14.3 策略要可解释

平台必须回答：

- 今天为什么买这只股票？
- 为什么卖出这只股票？
- 为什么今天空仓？
- 当前风险来自哪里？
- 这个策略比基准好在哪里？

### 14.4 平台要可运营

平台必须知道：

- 今天数据是否更新。
- 哪个任务失败了。
- 哪个策略运行失败了。
- 哪个策略触发风险。
- 哪个数据源异常。
