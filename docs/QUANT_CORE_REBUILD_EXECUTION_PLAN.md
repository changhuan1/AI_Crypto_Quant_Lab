# 量化内核重建执行计划

## 1. 为什么要重建量化内核

当前项目已经有了平台外壳：

- React 前端。
- FastAPI 接口。
- DuckDB 本地数据库。
- 策略对象。
- 一键回测。
- 净值、订单、持仓、成交展示。

但是它还不符合严谨量化研究的标准。主要问题是：

- 数据层没有完整处理 A 股历史成分股、停牌、ST、涨跌停、复权、交易日历。
- 回测引擎没有完整处理 T+1、100 股整数手、交易费用、印花税、涨跌停、停牌、成交约束。
- 策略研究流程缺少因子检验、样本外验证、参数稳定性、风险归因。
- 股票池现在仍容易产生幸存者偏差。
- 平台能展示结果，但还不能证明结果可信。

因此下一阶段的目标不是继续堆 UI，也不是马上增加更多策略，而是补齐“正常量化系统应该有的研究内核”。

## 2. 总目标

把项目从“能跑策略的平台”升级为“研究流程可信、回测逻辑可信、数据假设清楚的量化平台”。

最终应做到：

```text
数据标准化
  -> 因子研究
  -> 策略构建
  -> 专业回测
  -> 风险归因
  -> 模拟交易
  -> 平台展示
```

## 3. 第一阶段：数据标准层

### 3.1 目标

建立专业量化所需的标准数据表，不再只依赖一张 `prices_daily`。

### 3.2 要做什么

1. 建立交易日历表 `trading_calendar`。
2. 建立指数历史成分表 `index_constituents_history`。
3. 建立资产每日状态表 `asset_status_daily`。
4. 建立公司行为表 `corporate_actions`。
5. 建立数据质量报告表 `data_quality_reports`。

### 3.3 字段要求

`trading_calendar`：

- market
- date
- is_open
- previous_open_date
- next_open_date

`index_constituents_history`：

- index_id
- date
- asset_id
- weight
- source

`asset_status_daily`：

- asset_id
- date
- is_tradable
- is_suspended
- is_st
- is_limit_up
- is_limit_down
- up_limit
- down_limit
- listed_days

`corporate_actions`：

- asset_id
- ex_date
- action_type
- cash_dividend
- split_ratio
- source

### 3.4 验收标准

- 初始化数据库后能看到这些标准表。
- 即使暂时没有完整数据，也要有明确表结构。
- 回测引擎只能通过这些标准表判断交易限制。

## 4. 第二阶段：A 股交易规则

### 4.1 目标

把 A 股交易制度变成平台底层规则，而不是策略自己处理。

### 4.2 要做什么

1. 实现 T+1。
2. 实现 100 股整数手。
3. 实现买入不能超过现金。
4. 实现买入费用。
5. 实现卖出费用和印花税。
6. 实现停牌不能交易。
7. 实现涨停不能买。
8. 实现跌停不能卖。
9. 记录被拒绝订单原因。

### 4.3 验收标准

- 买入数量必须是 100 的整数倍。
- 资金不足时自动缩小买入数量。
- 停牌、涨停、跌停触发时订单状态为 rejected。
- 每笔订单都有原因。

## 5. 第三阶段：专业回测引擎

### 5.1 目标

把当前“目标权重净值计算”升级成“账户、订单、成交、持仓、现金流水”的专业回测。

### 5.2 要做什么

1. 信号日和成交日分离。
2. 默认使用下一交易日开盘价成交，避免未来函数。
3. 每日先计算组合市值。
4. 调仓时生成订单。
5. 订单经过风控和交易规则检查。
6. 通过规则后生成成交。
7. 更新现金、持仓、费用。
8. 保存每日持仓。
9. 保存订单和成交。

### 5.3 验收标准

- 交易发生在信号日之后。
- 订单表中有 rejected / filled。
- 成交表只记录真实成交订单。
- 净值、现金、持仓能互相对上。

## 6. 第四阶段：因子研究模块

### 6.1 目标

策略不能只看最终收益，还要知道因子是否真的有效。

### 6.2 要做什么

1. 计算 forward return。
2. 计算因子 IC。
3. 计算 Rank IC。
4. 计算分组收益。
5. 保存因子研究结果。
6. 前端展示因子研究摘要。

### 6.3 第一批因子

- 20 日动量。
- 60 日动量。
- 相对强弱。
- 成交额确认。
- 20 日波动率。
- A Share Market Score。

### 6.4 验收标准

- 每个因子能看到 IC 均值。
- 每个因子能看到 IC 胜率。
- 每个因子能看到分组收益是否单调。

## 7. 第五阶段：股票池修正

### 7.1 目标

减少幸存者偏差。

### 7.2 要做什么

1. 当前阶段先保存“当前成分股快照”到 `index_constituents_history`。
2. 后续接入历史成分股数据源。
3. 回测时按交易日读取当日股票池。
4. 没有历史成分数据时，必须在报告中标记“存在幸存者偏差风险”。

### 7.3 需要用户帮助

如果要真正消除幸存者偏差，需要稳定数据源：

- Tushare Pro token。
- JoinQuant 数据账号。
- Wind / Choice / iFinD。
- 或其他能提供历史指数成分股的数据源。

没有这些数据，也能做研究框架，但不能声称历史回测完全严谨。

## 8. 第六阶段：风险归因

### 8.1 目标

平台要能回答为什么赚钱、为什么亏钱、风险来自哪里。

### 8.2 要做什么

1. 计算最大回撤区间。
2. 计算持仓集中度。
3. 计算换手率。
4. 计算单票贡献。
5. 计算基准超额收益。
6. 计算市场状态下的收益。

### 8.3 验收标准

- 回测结果页能看到风险归因摘要。
- 能看到最大回撤发生在哪个区间。
- 能看到主要亏损贡献资产。

## 9. 第七阶段：实验管理

### 9.1 目标

每一次策略实验都可复现。

### 9.2 要做什么

1. 建立 `research_experiments` 表。
2. 保存策略参数。
3. 保存数据版本假设。
4. 保存样本区间。
5. 保存结果指标。
6. 支持多个实验对比。

### 9.3 验收标准

- 每次回测能追溯参数。
- 能比较不同参数版本。
- 能区分样本内和样本外。

## 10. 第八阶段：前端补齐

### 10.1 目标

让用户不看代码也能理解研究过程。

### 10.2 要做什么

1. 数据质量页面。
2. 因子研究页面。
3. 回测可信度提示。
4. 交易规则说明。
5. 订单拒绝原因展示。
6. 实验对比页面。

## 11. 当前立即执行清单

本轮先做第一批内核改造：

1. 扩展数据库标准表。
2. 实现 A 股交易规则模块。
3. 升级回测引擎支持下一交易日成交、100 股整数手、费用、涨跌停/停牌检查接口。
4. 新增数据质量模块。
5. 新增因子研究模块。
6. 在 API 中暴露数据质量和因子研究结果。
7. 更新 README 和前端提示。

## 12. 当前需要用户提供的帮助

目前可以先不阻塞开发。

但如果要真正达到专业量化级别，后续需要你决定数据源：

1. 是否申请 Tushare Pro token。
2. 是否使用聚宽/米筐等数据服务。
3. 是否只做个人学习版，接受 AKShare 的数据不完整。

我的建议：

- 短期继续用 AKShare 把框架做完整。
- 中期接入 Tushare Pro。
- 如果你要做接近生产的 A 股研究，最终必须有历史成分股、ST、停牌、复权、涨跌停等可靠数据源。
